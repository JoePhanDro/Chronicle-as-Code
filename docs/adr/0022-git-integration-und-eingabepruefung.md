# ADR 0022: Git-Integration, sicherer Aufruf und Prüfung fremder Vault-Inhalte

- **Status:** Vorgeschlagen (zu bestätigen). Überarbeitet nach Review (Sicherheit und Architektur).
- **Datum:** 2026-10-25
- **Bezug:** ADR 0012, ADR 0016, ADR 0017, `chronicle/sync.py` (`_run`, `_git`, `_use_merge_driver`), `chronicle/loader.py` (`find_topic_files`, `collect_evidence`), `chronicle/store.py` (`_atomic_write`, `folder_lock`), `chronicle/accounts.py`

## Kontext

Heute startet `sync.py` Git über `subprocess.run([...], capture_output=True)` mit einer Argumentliste (ohne Shell). Das ist die richtige Grundform. Es gibt aber noch keine einheitliche Stelle, keine Zeitlimits, keine Umgebungskontrolle und keine Prüfung von URLs oder Branch-Namen, weil bisher nur der eigene Ordner angefasst wurde. Mit Vaults kommen Inhalte hinzu, die andere Personen geschrieben haben und die ein Prüfer nur teilweise gesehen hat. Auch ein kompromittiertes Konto im Team kann Inhalte einspielen.

Das Review hat am Ist-Zustand (`main`) vier Lücken **belegt**, die unabhängig von Vaults gelten und im Plan als Teile 0a und 0b zuerst behoben werden:

1. **Code aus dem Vault wird ausgeführt.** Der Merge-Treiber läuft als `python -m chronicle.merge` mit dem Vault-Arbeitsverzeichnis als Arbeitsverzeichnis. Python setzt bei `-m` das aktuelle Verzeichnis an den Anfang des Suchpfads. Eine `yaml.py` oder ein Ordner `chronicle/` in der Vault-Wurzel wird importiert und ausgeführt.
2. **Abstürze durch YAML.** Etwa 120 KB tief verschachtelte `[` bringen den C-Lader (`CSafeLoader`) mit SIGSEGV zum Absturz. Eine Größenbegrenzung allein schützt nicht.
3. **Symlinks beim Schreiben.** `store._atomic_write` folgt einem Symlink `.ev-1.yaml.tmp`, `folder_lock` ebenso `.chronicle.lock`.
4. **`.git/config` eines vorhandenen Klons wird ausgeführt.** `core.sshCommand` in der Konfiguration läuft trotz bereinigter Umgebung und `-c`-Schaltern.

## Optionen für die Git-Anbindung

1. **Aufruf des `git`-Programms** (Shell-out, wie heute). Alle Fähigkeiten (Merge-Treiber, Signieren, SSH, Credential Helper, Teilklone). Ausgabe muss geparst werden.
2. **libgit2 (`pygit2`).** Kein Prozess, aber keine selbst definierten Merge-Treiber, Credential Helper und SSH-Signaturen nur eingeschränkt. Native Bibliothek als Abhängigkeit.
3. **Dulwich (reines Python).** Kaum Merge-Unterstützung.
4. **GitPython.** Wrapper um Option 1 mit zusätzlicher Angriffsfläche. Kein Gewinn.

## Entscheidung

**Option 1, in einem einzigen Modul `chronicle/git.py`.** Nirgends sonst im Code wird `git` gestartet (ein Test sucht nach `subprocess` außerhalb dieses Moduls). Das Modul erzwingt:

### Aufruf

1. **Programm und Version.** Der Pfad zu `git` wird beim Start einmal aufgelöst (`shutil.which`) und festgehalten. Die Version wird beim Start geprüft: mindestens der **gepatchte Stand ab 2.45.1** beziehungsweise die aktuelle Wartungsversion des Verteilers. Die Zahl 2.39 aus dem ersten Entwurf entfällt, sie schützt nicht. Der Reviewer nennt CVE-2024-32002 (Submodule beim Klonen) und CVE-2025-48384 (Zeilenende und Submodule) als Gründe. **Beide Angaben sind vor der Umsetzung gegen die aktuellen Hinweise des Git-Projekts zu verifizieren**, sie sind hier nicht aus eigener Prüfung übernommen. Ist Git zu alt, startet der Server ohne Schreib- und Sync-Funktionen und sagt das.
2. **Arbeitsverzeichnis.** `git.py` setzt das Arbeitsverzeichnis ausdrücklich (`cwd=` auf den Vault-Pfad nur dort, wo Git es braucht). **Das Arbeitsverzeichnis des Merge-Treibers bleibt die Vault-Wurzel** (Git bestimmt es). Der Schutz vor Code aus dem Vault kommt nicht vom Arbeitsverzeichnis, sondern vom Start des Treibers (Punkt 18). **Die Anwendung selbst wird nie mit dem Vault als Arbeitsverzeichnis gestartet** (Startprüfung: das aktuelle Verzeichnis liegt nicht im Vault).
3. **Aufruf.** Immer eine Liste, nie `shell=True`. Immer `git -C <vault-pfad>` mit einem Pfad aus der geprüften Registry (ADR 0014). Werte aus Benutzereingaben stehen nie an der Stelle einer Option: Pfade nach `--`, Refs nach `--end-of-options` oder durch eine Prüfung gegen ein festes Muster.
4. **Namen von Branches und Benutzern.** Eine einzige Funktion `branch_slug()` erzeugt den Namen aus Klon-Kennung und Datum, mit festem Muster `^chronicle/[a-z0-9][a-z0-9._-]{0,63}/[a-z0-9][a-z0-9._-]{0,63}$` und `re.fullmatch`. Zusätzlich prüft `git check-ref-format --branch`. Dasselbe gilt für Benutzernamen: `USERNAME_PATTERN` in `accounts.py` nutzt `re.match` mit `$` und akzeptiert `"anna\n"` (belegt, Fehler auf `main`). Alle Muster verwenden `fullmatch` oder `\Z`.
5. **Umgebung.** Eine ausdrückliche Auswahl statt Weitergabe von allem. Zugelassen: `PATH`, `HOME`, `LANG`, `LC_ALL=C`, `SSH_AUTH_SOCK`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS` und die Variablen, die der konfigurierte Credential Helper braucht (siehe Test-Matrix in Punkt 25). Gesetzt: `GIT_TERMINAL_PROMPT=0`, `GIT_ALLOW_PROTOCOL=https:ssh`, `GIT_CONFIG_GLOBAL` und `GIT_CONFIG_SYSTEM` **bewusst** (Standard: die Dateien des Benutzers, damit Credential Helper und Signierung funktionieren; auf Wunsch eine eigene, minimale Datei in `CHRONICLE_HOME`). Autor und Committer aus ADR 0015. Nicht weitergegeben: `GIT_DIR`, `GIT_SSH_COMMAND`, `GIT_EXTERNAL_DIFF`, `GIT_EXEC_PATH` und ähnliche.
6. **Feste Konfiguration pro Aufruf** (`-c`): `protocol.ext.allow=never`, `protocol.file.allow=never` (Tests setzen es ausdrücklich), `core.hooksPath=<leerer Ordner>`, `core.fsmonitor=false`, `core.sshCommand=ssh` (überschreibt einen Wert aus `.git/config`), `core.pager=cat`, `core.editor=true`, `submodule.recurse=false`, `transfer.fsckObjects=true`, `fetch.fsckObjects=true`, `core.autocrlf=false`, `core.eol=lf`, `core.safecrlf=false`. SSH läuft mit `BatchMode=yes` und `StrictHostKeyChecking` wie vom Benutzer konfiguriert (kein stilles Akzeptieren neuer Schlüssel).
7. **Prüfung der Konfiguration eines vorhandenen Klons (`vault add`).** `.git/config` ist Code: Schlüssel wie `core.sshCommand`, `core.fsmonitor`, `core.hooksPath`, `core.pager`, `credential.helper`, `url.*.insteadOf`, `filter.*`, `diff.*.textconv`, `include.path` werden von Git ausgeführt oder umgeleitet, und ein `-c` auf der Befehlszeile deckt nicht alle Fälle ab. `vault add` liest die Konfiguration mit `git config --local --list -z` und akzeptiert nur eine **Allowlist**: `core.repositoryformatversion`, `core.filemode`, `core.bare`, `core.logallrefupdates`, `core.symlinks`, `remote.origin.url`, `remote.origin.fetch`, `branch.*`, `merge.chronicle.*`. Alles andere führt zur Ablehnung mit Hinweis. Alternativ akzeptiert die App nur Klone, die sie selbst angelegt hat (`vault clone`). Die Registry speichert die **erwartete URL von `origin`**. Vor jedem `fetch` und `push` vergleicht `git.py` sie mit der Konfiguration und bricht bei Abweichung ab.
8. **Netzzugriff nur für die benötigten Refs.** `fetch origin +refs/heads/<standard>:refs/remotes/origin/<standard>` (und der eigene Arbeits-Branch), nicht `fetch origin` für alles. Der Push nennt genau einen Ref. Das begrenzt, was ein vorhandener SSH-Agent im Namen des Benutzers tun kann. Empfehlung für Betreiber (Dokumentation): für jeden Vault eigene Zugangsdaten (Deploy Key oder fein granulares Token) mit `IdentitiesOnly=yes`, damit der Agent nicht alle Schlüssel anbietet.
9. **Klonen.** `git clone --no-recurse-submodules -c core.symlinks=false -- <url> <pfad>`. `core.symlinks=false` hilft nur bei **frischen** Klonen (Git legt Links als Dateien mit dem Linkziel an). Die eigentliche Absicherung ist die Prüfung nach Punkt 15 und 16.
10. **URLs.** Erlaubt sind `https://host/pfad`, `ssh://[user@]host/pfad` und die SCP-Form `user@host:pfad`. Abgelehnt: `ext::`, `file:`, `git:`, `http:`, Zugangsdaten in der URL, Steuerzeichen, Leerzeichen, ein führendes `-`. Optional eine Liste `allowed_hosts` in der Registry. Fehlermeldungen und Logs entfernen `://…@`.
11. **Zeitlimits und Größen.** Netzwerkbefehle 60 Sekunden, lokale 10 Sekunden (einstellbar), danach wird die Prozessgruppe beendet. Die Ausgabe ist auf 16 MiB begrenzt.
12. **Ausgaben parsen nur mit stabilen Formaten:** `-z`, `--porcelain`, `--name-status`, `rev-parse`. Nie die menschenlesbare Ausgabe. Wo Umbenennungen keine Rolle spielen, steht `--no-renames`.
13. **Keine Git-Konfiguration des Benutzers ändern.** Nur lokale Konfiguration des Klons (`--local`): Merge-Treiber, `core.symlinks`.
14. **Fehler.** Ein Ausnahmetyp (`GitError`, heute `SyncError`) mit bereinigter Meldung. Die rohe Ausgabe von Git geht nur ins Protokoll auf Debug-Stufe.

### Prüfung von Inhalten aus dem Vault (Eingabe ist nicht vertrauenswürdig)

Alles, was aus einem Vault gelesen wird, gilt als Eingabe von außen. Die gemeinsame Prüfung (`chronicle check`, Schreibpfad, Index, Merge-Treiber, `base_timelines` in `sync.py`, Vault-CI) erzwingt dieselben Regeln, aus **einem** Modul.

15. **Keine symbolischen Links und keine Submodule.** Im Dateisystem sind **Links im ganzen Baum ein Prüffehler**: Ein Durchlauf mit `os.scandir` (statt `rglob`) prüft jeden Eintrag per `lstat`. Der Datenordner selbst darf ein Link sein (z. B. ein Verweis auf den Ort des Klons), nur Einträge darunter nicht. Schreibpfad und Index weisen Links ebenfalls ab. Heute folgt `rglob` Dateilinks; ein Link `x.yaml` auf `~/.ssh/id_ed25519` würde gelesen.
    **Im Merge-Ergebnis** listet die App `git ls-tree -r` und weist Modus `120000` (Link) und `160000` (Gitlink/Submodul) ab. Bei einem Treffer wird der Merge mit **`git reset --merge`** zurückgenommen, **nicht mit `reset --hard`** (`--hard` verwirft auch nicht committete Änderungen und ist dieselbe Fehlerklasse wie Issue #126). `.gitmodules` wird nicht eigens abgewiesen: Ohne Gitlink im Baum bleibt sie wirkungslos, und `submodule.recurse=false` ist gesetzt.
    **Ein Link im Remote sperrt den Vault nicht dauerhaft:** Das Lesen des Basisstandes (`base_timelines`) überspringt Links, abgelehnt wird nur im Merge-Ergebnis. Sonst könnte ein einzelner eingespielter Link jede künftige Vorschau und jeden Abgleich blockieren (Fehler, der in PR #138 behoben wurde).
16. **Sicheres Schreiben.** Temporäre Dateien entstehen mit `os.open(..., O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW)` oder `tempfile.mkstemp` im selben Ordner (nicht unter einem vorhersagbaren Namen wie `.ev-1.yaml.tmp`). Vor `rename` wird das Ziel per `lstat` geprüft. Die Sperrdatei `.chronicle.lock` wird mit `O_NOFOLLOW` geöffnet; ist sie ein Link, bricht die App ab. Das schließt die Lücke aus dem Kontext (Punkt 3).
17. **Schutz der Vault-Wurzel in zwei Stufen.** **Umgesetzt ist zunächst eine Blocklist** (PR #138): Dateien mit den Suffixen `.py`, `.pyc`, `.pyw`, `.pyd`, `.so` (auch mit Tags wie `.cpython-312-x86_64-linux-gnu.so`), Ordner mit `__init__.*` und die Namen `chronicle`, `sitecustomize`, `usercustomize` sind Prüffehler. **Die volle Allowlist folgt in Teil 5** des Plans: `check` und die CI lehnen dann alle unbekannten Dateien und Ordner in der Wurzel ab. Erlaubt sind: `vault.yaml`, `topics/`, `evidence/`, `.github/`, `.gitignore`, `.gitattributes` (nur Zeilen aus Punkt 22), `README.md`, `docs/`, `.chronicle-secrets-allow`. Eine `yaml.py`, `chronicle/` oder `sitecustomize.py` in der Wurzel ist damit ein Prüffehler. Das ist die zweite Schicht neben Punkt 18.
18. **Der Merge-Treiber ist Ausführung von Code und startet so, dass der Vault nicht im Suchpfad steht.** `merge.chronicle.driver` ist `<sys.executable> -P -c <Start> <Paketordner> %O %A %B`.
    - **`-P` statt `-I`:** `-P` nimmt das Skript- und Arbeitsverzeichnis nicht in `sys.path` auf. `-I` hätte zusätzlich User-Site und `PYTHONPATH` abgeschaltet und damit Deployments mit `pip --user` gebrochen (Erkenntnis aus PR #138).
    - **Der Paketordner** (der Ordner, der `chronicle/` enthält) kommt aus `__file__` der laufenden App und **nie aus dem Vault**.
    - **Der kleine Start** (`<Start>`, ein paar Zeilen) entfernt das aktuelle Verzeichnis und leere Einträge aus `sys.path`, fügt den Paketordner hinzu und ruft `chronicle.merge.main` auf.
    - **Das Arbeitsverzeichnis des Treibers bleibt die Vault-Wurzel** (Punkt 2). Der Schutz kommt vom `-P`-Start, nicht vom Arbeitsverzeichnis.
    - **Ein Absturz des Treibers ist ein Fehler, kein Konflikt:** Nur Exit-Code 1 mit der Konfliktmeldung zählt als Konflikt, jeder andere Ausgang bricht den Abgleich mit einer Fehlermeldung ab (ADR 0017, Punkt 4). Das Kommando kommt aus der App, nie aus dem Vault: Eine `.gitattributes` im Vault darf `merge=chronicle` nennen, aber kein anderes Programm festlegen, weil Treiber nur aus der lokalen Konfiguration kommen (Punkt 22).
19. **Strenger Vorabscan statt blindem Laden.** Vor jedem Laden einer YAML-Datei aus einem Vault läuft ein Scan über den **Ereignisstrom** von `yaml.parse` (nicht `yaml.compose`, das Aliase auflöst und für ihre Erkennung nicht taugt). Der Scan ist etwa 40 Zeilen, er ist **kein eigener Parser**: Er zählt und lehnt ab. Abgelehnt werden: Verschachtelungstiefe über 12, Anker, Aliase, Tags (außer den Standard-Tags der Kernschemata), Merge-Key `<<`, doppelte Schlüssel in einem Mapping, mehr als 20.000 Knoten, Schlüssel, die keine Zeichenketten sind. Erst danach lädt der `SafeLoader`. Für Fremdinhalt ist der **reine Python-Lader** vorzuziehen (`yaml.SafeLoader` statt `CSafeLoader`): Er löst bei Tiefe eine Python-Ausnahme aus statt eines Absturzes. Die Geschwindigkeit des C-Laders (Issue #96) bleibt für eigene, geprüfte Dateien erhalten. Der Scan läuft auch im Merge-Treiber, in `base_timelines` und in der CI.
20. **Größenbegrenzung vor dem Lesen:** Event- und Topic-Datei höchstens 256 KiB, `vault.yaml` 16 KiB, Gesamtzahl der Dateien unter `topics/` höchstens 200.000. Die Größe wird mit `lstat` geprüft. Die Grenze ist notwendig und **nicht ausreichend** (Punkt 19).
21. **Zeichen und Werte.** Steuerzeichen (außer Zeilenumbruch und Tab) und Bidi-Steuerzeichen (U+202A bis U+202E, U+2066 bis U+2069) sind in allen Textfeldern verboten, ebenso in `vault.yaml`. Keys sind auf das ASCII-Muster beschränkt. Gleich aussehende ASCII-Zeichen (`l`/`1`, `O`/`0`) sind eine Restgefahr: Die Prüfung warnt bei Keys, die sich nur durch solche Zeichen von einem vorhandenen Key unterscheiden (Homoglyphen, Warnung). YAML-1.1-Eigenheiten von PyYAML (`no`, `on`, `yes` als Wahrheitswert, `1:30` als Sexagesimalzahl) werden im Schema über strikte Typen abgefangen: Textfelder verlangen Zeichenketten, Zahlen und Booleans in Textfeldern sind Fehler.
22. **Attribute und Zeilenenden.** `.gitattributes` im Vault darf nur Zeilen enthalten, die die Vorlage vorgibt (`merge=chronicle` für Topic- und Event-Dateien, `evidence/** binary`); alles andere (`filter=`, `diff=`, `eol=`, `text=auto`, `ident`) ist ein Prüffehler. Die App schreibt zusätzlich in `.git/info/attributes`: `evidence/** -text -ident -filter binary`. Pro Aufruf stehen `core.autocrlf=false`, `core.eol=lf`, `core.safecrlf=false` (Punkt 6). Damit verändert Git keine Anhänge, und die Prüfsumme bleibt stabil.
23. **Pfade.** Dateiname und Ordner entsprechen dem Key-Muster (ADR 0013). Anhangspfade enthalten kein `..`, kein Laufwerk, keinen führenden `/` und liegen unter `evidence/`. Der Schreibpfad setzt Pfade nie aus Eingabe zusammen, ohne `is_relative_to` zu prüfen. Auf Dateisystemen ohne Unterscheidung von Groß- und Kleinschreibung (macOS, Windows) prüft die Anwendung **auch lokal** auf Keys, die sich nur in der Schreibweise unterscheiden.
24. **Ausgabe und Meldungen.** Markdown wird bereinigt (`nh3`, `html: False`, wie heute). Anhänge werden mit `Content-Security-Policy: sandbox` und `nosniff` ausgeliefert (ADR 0004). **Fehlermeldungen geben keinen Dateiinhalt wieder:** Die Pydantic-Modelle setzen `hide_input_in_errors=True`, Meldungen nennen Datei, Feld und Regel und werden auf eine Zeile gekürzt (heute enthält `Schema-Validierung fehlgeschlagen` den Wert, `input_value=…`, also Inhalt einer Datei, die nicht zu den Daten gehört, etwa ein Link-Ziel).
25. **Test-Matrix für Umgebung und Credential Helper.** Die Einschränkung der Umgebung (Punkt 5) bricht leicht Credential Helper, GPG/SSH-Signierung, `DBUS`, `XDG_RUNTIME_DIR` und den Git Credential Manager. Vor Teil 3 des Plans wird in einer Matrix geprüft: macOS Keychain, Linux libsecret, Git Credential Manager, `ssh-agent` mit Schlüsseldatei, SSH-Signierung, GPG-Signierung. Die Whitelist wird aus dem Ergebnis abgeleitet, nicht geraten.

### Vault-CI

26. Die Prüfung im Vault läuft als **wiederverwendbarer Workflow** des Code-Repositorys, **per Commit-SHA angeheftet**, mit `on: pull_request` und `merge_group` (nicht `pull_request_target`), `permissions: contents: read` und ohne Secrets. Sie installiert die Abhängigkeiten aus `requirements.txt` des Code-Repositorys mit `pip install --require-hashes`, nicht aus dem Vault. Das Pinning gilt doppelt (SHA des Workflows und SHA des Code-Repositorys als Eingabe). Der Check wird **nie** durch `paths-ignore` oder `if:` übersprungen, wenn er erforderlich ist (ein übersprungener Job gilt auf GitHub als bestanden). Details und Vorlage in ADR 0016, Punkt 9.

### Der Server selbst

27. **Host-Prüfung.** Der Server prüft den `Host`-Header gegen die konfigurierten Namen (`TrustedHostMiddleware`) und bei schreibenden Anfragen `Origin` oder `Referer`, zusätzlich zum CSRF-Token. Das schützt gegen DNS-Rebinding auf `127.0.0.1` (Arbeitsplatz-Modus).

## Konsequenzen

- Eine Abhängigkeit weniger (kein libgit2), aber die Pflicht, Aufrufe sauber zu halten. Der Test „kein `subprocess` außerhalb von `git.py`“ verhindert Abkürzungen.
- Die Punkte 15 bis 19 betreffen schon `main` und werden als **Teile 0a und 0b** des Plans vorgezogen, unabhängig vom Rest.
- Der reine Python-Lader ist langsamer. Für Fremdinhalt (Merge, Klon, CI) ist das vertretbar, für den laufenden Index zählt das Ergebnis aus `scripts/measure_index.py` (10.000 Dateien, Vollaufbau 0,63 s laut Review).
- Windows ist nicht Ziel (ADR 0014).

## Offene Punkte

- Genaue Mindestversion von Git nach Verifikation der Hinweise (Punkt 1).
- Ob `allowed_hosts` Pflicht werden soll. Vorläufig optional.
